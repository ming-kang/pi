# plan — read-only plan mode

Adds `/plan` for a Claude-Code-style planning phase: the model explores with read-only tooling, interviews the user, and leaves the mode through a user-approved `exit_plan` tool call that saves the plan to disk and optionally compacts the context before execution starts.

## Behavior

- `/plan` (or the `--plan` CLI flag) enters plan mode. On entry the active tool set is snapshotted and swapped to the exploration set: `edit` and `write` are deactivated, the standalone `grep`/`find`/`ls` search tools (registered but not active by default) are activated alongside `read`, and `bash` stays available but is constrained to read-only inspection by the plan-mode system prompt (git log/diff/blame/show/status, ls, wc, head, tail, cat, …) — the same contract as the explorer subagent. The bundled `subagent` tool stays active but only the built-in read-only `explorer` profile is allowed. Other extension tools (`question`, `todo`, `deepwiki`, …) stay available. A `tool_call` guard also covers requests already in flight when the mode toggles: it blocks `edit`/`write` and any `subagent` call whose profile (including the omitted-default `general`, and every task in `tasks` mode) is not `explorer`.
- While planning, the system prompt gains a plan-mode block: explore before asking, interview one decision at a time with the `question` tool (with a recommendation and trade-offs), skip the interview for small clear tasks, then present the full plan as response text before calling `exit_plan`.
- `exit_plan(title, plan, revises?)` opens the approval menu. Each option carries a muted description, and the dialog subtitle reports context usage as `Context 29.4% of 200k` when the window is known (or just the percentage otherwise) — the fact the compact-or-not decision turns on:
  - **Start executing** *(keep full context)* — saves the plan, restores tools, and execution continues in the same run.
  - **Compact context, then execute** *(best for long tasks)* — saves the plan, ends the run (`terminate`), compacts once the run has settled, and only then restores tools; execution restarts via a kickoff message that embeds the plan text, so continuation never depends on the compaction summary. If compaction fails, tools are restored and execution proceeds with full context.
  - **Keep planning** *(refine before running)* — optionally collects feedback (multi-line editor in the TUI, input dialog in RPC) and returns it to the model; plan mode stays active. `Esc` and dialog timeouts map here, never to an executing option, so the dismiss hint reads "keep planning" rather than "cancel".
- Both executing options save the plan file. If the session has no name yet, the plan title becomes the session name.
- `/plan` while planning opens the plan panel (TUI): the first option exits plan mode, the rest are saved plan files — this branch's plans first, then the project's, newest first, bounded at 20. Picking a file pastes its absolute path into the editor so the user can add an instruction around it; `Esc` keeps planning with no side effects. Outside the TUI the command keeps the direct-toggle semantic. During a pending compaction the command is refused until the compaction settles.
- Plan files live under `<agentDir>/plans/<safeCwdDir>/<YYYYMMDD-HHmm>-<slug>.md` (`~/.pi/agent/plans/…` by default, `PI_CODING_AGENT_DIR` respected), grouped per project with the same cwd encoding as sessions, with `title`, `created`, `cwd`, `session`, and optional `revises` frontmatter. The local-time stamp keeps names chronologically sortable; same-minute collisions append `-2`, `-3`, …. Revisions are new files that point back via `revises`. Plans saved before the per-project layout stay in their legacy `plans/<sessionId>/` directories and remain reachable through the branch's recorded paths.
- To revise a plan mid-execution, re-enter with `/plan`: the system prompt lists the branch's saved plans so the model reads the latest one, accounts for completed work, and produces a revision.

## Limits

- The kickoff message embeds at most 24 000 characters of plan markdown; longer plans are truncated with a pointer to the full file.
- In `json`/`print` modes `exit_plan` cannot ask, so it saves the plan and exits with context kept (write access is restored without a menu).
- Approving with **Compact context, then execute** and then interrupting before compaction completes (quit, resume, branch switch) degrades to the keep-context exit on the next session start.
- The dialog subtitle is omitted when context usage is not yet known (no assistant turn has reported usage).
- The read-only bash constraint is prompt-enforced, not sandboxed — the same trust model as the explorer subagent.

## Implementation notes

- **Conversation-backed state.** Every transition appends a `plan-mode` custom entry (never sent to the LLM); lifecycle handlers replay the current branch tail → head, so `/reload`, `/tree`, resume, and fork restore the mode. Fork and clone copy entries, so the recorded plan-file paths follow the new session even though it gets a fresh session id — the plans directory is only the initial storage location, not the index.
- **State is keyed per session id** (todo pattern): resume and `/tree` can switch sessions within one process, and handlers re-point the active bucket before touching state.
- **Tool restore is a snapshot, not an inverse delta.** Entry records the full pre-entry active set and exit restores it verbatim — necessary because entry both removes (`edit`/`write`) and adds (`grep`/`find`/`ls`) tools. Replay keeps the in-memory snapshot across branch switches while planning (re-snapshotting would capture the restricted set) and treats legacy `removedTools` entries as an empty snapshot, which degrades to dropping `exit_plan` only.
- **No write access is ever needed for the plan itself** — the plan text travels as an `exit_plan` parameter and the extension writes the file.
- **The compact-then-execute window is closed by construction**: plan mode (and its tool restrictions) persists until compaction completes; the run is terminated by the tool result and the compaction starts on `agent_settled`, which fires once per fully settled run.
- The `exit_plan` result text authoritatively announces mode changes because the per-run system prompt override is not rebuilt mid-run.
- **The tool row renders from the title and `details`, not from the parameters.** `exit_plan` carries the whole plan as a parameter, and its result text is written for the model, so the default renderer would echo the plan markdown escaped onto one line and then restate tool-state rules at the user. The collapsed call shows the title; expanding renders the complete plan with Pi's standard Markdown theme while keeping `revises` metadata muted. Results give the decision normal emphasis, keep `Saved to` secondary, and warn when historical state says no approval was pending. Malformed historical decision/path values fall back safely to the bounded model text.
